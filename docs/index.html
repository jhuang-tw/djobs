Local repository memory over MCP

Your next AI session should remember yesterday.

djobs lets coding agents recover goals, constraints, failed approaches, progress, and Git changes from a small local memory — then use explicit checkpoint and handoff only when coordinated work actually needs ownership.

Why djobs

Stop paying the restart tax on every new chat.

A coding agent may already know the failed approach, the project constraint, the remaining test, and the exact files it changed. djobs keeps that context attached to the repository instead of the chat window.

◉

Local-first memory

Goals, observations, session capsules, and task state stay in local SQLite. No broker, daemon, cloud database, or hosted login.

⌕

Relevant recall

The current request searches older memory, so a useful constraint or failed approach can rank above newer unrelated activity.

↗

Worktree-aware handoff

Sibling worktrees share passive repository memory while explicit ownership and leases stay isolated to each checkout.

How it works

Capture, search, continue.

Ordinary sessions use passive memory. Exact task ownership remains an explicit action, so observation never silently becomes control.

Observe the session

Bounded user intent, tool results, failures, Git changes, and a deterministic session capsule are stored as local data.

Search for the request

sync_workspace(query=...) retrieves the most relevant repository memory under a token budget.

Continue with evidence

The agent resumes from the useful state and can checkpoint or hand off exact work only when coordination requires it.

Clear boundaries

Memory is not task ownership.

djobs separates what the repository remembers from who owns a unit of work.

Passive project memory

Best for normal vibe-coding sessions and context recovery.

  • user goals and constraints
  • successful and failed tool results
  • Git working-tree observations
  • session capsules and memory lifecycle states
  • query-aware recall with unchanged-context suppression

Explicit checkpoint and handoff

Best for coordinated tasks that need exact ownership.

  • checkout-scoped leases
  • bounded completion or release evidence
  • safe worktree isolation
  • no silent prompt-to-task conversion
  • lower-level queue tools available only when requested

Install

One install, then open any repository.

The VS Code extension is the easiest route. Other MCP hosts can launch djobs through uvx. Setup and doctor remain repair tools, not a ritual for every project.

Reproducible benchmarks

Show the payload, not a vague marketing number.

The bundled deterministic fixture compares a full synthetic repository reread with one query-aware recovery call.

~7,805estimated tokens to reread the synthetic 18-file fixture
~407estimated tokens for query-aware sync_workspace

A 94.8% recovery-payload proxy reduction for this fixture. This is not provider billing, latency, or model-quality measurement. Run python scripts/benchmark_project_memory.py and inspect it yourself.

Privacy and control

Local, inspectable, and reversible.

State defaults to ~/.djobs/global.db. Common credentials are redacted on a best-effort basis, stored text is untrusted data, and failures remain fail-open.

Opt out per prompt

Add [djobs:no-memory] when a request should not be stored.

✓

Resolve without erasing

Mark memory resolved, superseded, stale, or contradicted while keeping the audit trail.
